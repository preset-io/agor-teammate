## Sentry access is `scripts/sentry.py` + `SENTRY_API_TOKEN`, NOT the Sentry MCP connector

Whiffed on this in a session with Elizabeth: she asked about Sentry deprecation trends and I
answered that I "can't reach Sentry — MCP needs OAuth, non-interactive session can't auth." That's
half-true but misleading. The **Sentry MCP connector** OAuth *has* been broken since 2026-08-10
(RFC 9207 / SEP-2468 issuer mismatch) — but Elizabeth already got me a static **Internal Integration
token** (`SENTRY_API_TOKEN`, present in env) that `scripts/sentry.py` uses over the plain REST API.
That's the standing Sentry path and it works fine (`search` / `volume-delta` / `issue`).

**How to apply:** When Sentry comes up, reach for `./scripts/sentry.py` first — don't announce the
MCP connector as a dead end. The token being "gotten for me" is a fact Elizabeth remembers even when
I don't; conflating the two access paths reads as forgetting work she did.

## Never attribute a workspace from EC2 node/host IDs on a multi-tenant cluster

**What happened:** Investigating a ~11:30 PT chart/data "burst" on us1a, I saw many async-task
logs on hosts i-074248e6d2d958abf / i-085fae5964e3f09aa — the same nodes that served 2cad1810's
dashboard 484 — and told the user the burst was 2cad1810. Wrong: namespace-filtered counts showed
only 5 of ~74 async tasks were 2cad1810. Those nodes run pods from many workspaces.

**Why:** Preset prod clusters are multi-tenant; a k8s node hosts many workspaces' pods, so the
Datadog `host:` field (EC2 instance) tells you nothing about which workspace/tenant made a request.

**How to apply:** To attribute activity to a workspace, filter/group by **kube_namespace**
(ws--<deployment-slug>--main), or read the **nginx access-log `host:` header** (the
`<wsname>.us1a.app.preset.io` hostname) — that's the only field that names the tenant. Note
`get_logs` output does NOT include kube_namespace per line and returns empty messages for nginx
access logs; the buffered-body warn logs DO embed the full request + workspace host header, which is
how I finally identified 87d40918 "Analytics Playground" / dashboard 114. Also: a workspace with
0 "Created new async task" logs has Global Async Queries OFF (chart/data runs synchronously). [[MEMORY]]

## Datadog Cost Management API access
- Real Datadog $ (not just usage) is reachable via `/api/v2/usage/historical_cost` (finalized months, lags ~1mo) and `/api/v2/usage/estimated_cost` (current + recent est). Param `view=summary` (NOT `sub`). Headers `DD-API-KEY` + `DD-APPLICATION-KEY`.
- Env vars: use **`DD_APP_KEY`** as the application key — `DATADOG_APP_KEY` is stale (401). Either API key (`DATADOG_API_KEY`/`DD_API_KEY`) works. Site `datadoghq.com`.
- The Birds MCP `query_metrics` tools only expose `datadog.estimated_usage.*` VOLUME, never dollars — for $ you must hit the Cost API directly via curl with these keys.

## Soraya Slack gateway — inbound replies broken (missing scope)
Symptom: humans @-mention @Soraya in a bot-posted thread (#agor-cloud, C0B6SR8MEP7) but nothing comes back; no session spawns.
Root cause: the Soraya Slack app bot token is **missing `channels:history`**. Proven: `agor_gateway_slack_thread_history_get` → `missing_scope`. Chain: `app_mention` fires → gateway tries to hydrate thread via Slack history API → missing_scope → inbound aborts → no session created (verified via agor_sessions_list on branch — no session seeded from thread).
NOT the cause: `require_mention:true` (mention was present); `allowed_channel_ids:[]` = all-allowed.
Fix: add `channels:history` (+channels:read, chat:write.public, groups:read, mpim:history, users:read.email) in api.slack.com → OAuth & Permissions → **reinstall app** (rotates xoxb-) → save new token to gateway channel `019edd38-92af-73a4-9691-a3a8c55ce4f4` via `agor_widgets_request_gateway_token`. Outbound (`chat:write`) already works. Correct manifest available via `agor_gateway_slack_manifest_generate(appName=Soraya, publicChannels=true, outbound=true, threadHistory=true)`.
