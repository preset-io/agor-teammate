
## Dividing connections by replicas is the fastest way to characterize a pg saturation
`max:aws.rds.database_connections{...}/max:kubernetes_state.deployment.replicas_available{...}` as a single Datadog query answers "leak vs fixed-pool-times-replicas" in one shot. A **flat** ratio over days = fixed per-pod pool, so the trigger is a scale-out event, not a leak. A **climbing** ratio = real leak. Today this collapsed the whole cord-shell triage into one query and let me rule out "connection leak" and "DB capacity" exactly as the handoff asked.
Corollary: always pull the ratio over ~7d, not just the incident window. The incident window alone shows saturation; the 7-day baseline is what proves the per-pod footprint was unchanged and isolates *what actually changed today* (replica count).

## Search Shortcut for the mechanism, not just the symptom
"cord too many clients" -> 0 results. "cord max_connections" -> **sc-83354**, the same incident from before with the same three fixes already written down. Symptom strings are log-specific and rarely in a story title; the resource/limit name is. Finding the prior story reframed the whole writeup from "new bug" to "recurrence, previous mitigation insufficient" — much more actionable for the owner.

## Check whether the runbook actually applies before following it
The "High DB Load / High Connection Count" runbook looked like an exact match by title and would have had me hunt an offending user and `pg_terminate_backend` the top 5 sessions. It assumes a *superset* DB with a workspace user leaking `idle in transaction`. Here the connections were legitimately held by the service's own pools across 5 pods — terminating them would have churned the pods and done nothing. Read the runbook's assumptions, not just its name.
