### Picked: `SUPERSET-PYTHON-13JV` — `load_chart_data_into_cache` re-raises validation-class errors as unhandled Celery exceptions

908 events/14d, 0 users, chronic since 2026-05-22, still firing (last event during this run).

**Root cause** (verified via raw event JSON — confirmed a genuine `exception` entry with app-level frames, not log noise): `superset/tasks/async_queries.py::load_chart_data_into_cache` catches every exception from `ChartDataCommand.run()` in one generic `except Exception` block, reports it to the client via `async_query_manager.update_job(...)`, then unconditionally re-raises — including `ChartDataQueryFailedError` (raised in `get_data_command.py` when a chart still references columns dropped from its dataset, i.e. customer-side schema drift). This is inconsistent with the *synchronous* `/api/v1/chart/data` endpoint: `ChartDataRestApi._get_data_response` explicitly maps `ChartDataQueryFailedError`→400 and its sibling `ChartDataCacheLoadError`→422 — both already classified elsewhere in the same codebase as expected client-facing validation failures, not server bugs. Because the async task always re-raises, Celery's default task-failure handling (and Sentry's Celery integration) captures every occurrence as an unhandled ERROR, duplicating what `update_job` already reported cleanly. Confirmed no `.get()`/retry policy/result-backend consumer exists for this fire-and-forget `apply_async` task (grepped all callers), so nothing depends on the task's own exception/FAILURE state for these two types.

Note: the existing test `test_load_chart_data_into_cache_with_error` used `ChartDataQueryFailedError` as its exception, but only incidentally — the test itself is about generic exception handling, not a deliberate pin on this specific type always re-raising. Repointed it at `RuntimeError` to keep testing the generic path and avoid it colliding with the new carve-out.

**Fix** (branch `fix-chartdata-query-failed-celery-noise`, apache/superset shared clone at `/home/agorpg/.agor/repos/superset` — worked directly in the shared clone, no dedicated Agor branch created, matching 08-22's precedent since direct writes worked fine today, no EACCES): added a dedicated `except (ChartDataCacheLoadError, ChartDataQueryFailedError)` branch before the generic handler — still calls `update_job(..., STATUS_ERROR, ...)`, logs at INFO, does not re-raise. All other exception types (including SIP-40 `SupersetErrorException`/`SupersetErrorsException`) untouched.

**Tests**: `tests/unit_tests/tasks/test_async_queries.py` — repointed the generic-error test at `RuntimeError`, added two new tests (`ChartDataQueryFailedError` and `ChartDataCacheLoadError` don't re-raise, still report via `update_job`). 9/9 passing (borrowed `superset_core` via `PYTHONPATH=/tmp/bug-triage-repos/superset-private/superset-core/src`, standard workaround for [[project_superset_shared_repo_pytest_env_broken]]). `ruff check` + `ruff format --check` clean (ruff 0.9.7, the CI-pinned version — no stale-hook issue today, see [[project_superset_shared_repo_stale_ruff_hook]]).

**Tradeoff disclosed** (PR body + Shortcut description + Minerva prompt, all three): this is a genuine failure-mode semantics change, not a pure log-level tweak — the Celery task now completes without raising for these two exception types even though the chart query itself failed. Client-facing behavior is unchanged (still delivered via `update_job`/job-status poll). Verified and disclosed the "nothing depends on task-level exception state" claim rather than self-ratifying it — asked both self-review and Minerva to independently check it.
