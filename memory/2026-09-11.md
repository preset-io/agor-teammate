**Picked: SUPERSET-PYTHON-12QC** — https://preset-inc.sentry.io/issues/7450117832/ — `ToolError: 'search_tools' is a synthetic search tool and cannot be called via the call_tool proxy`, 552 events, firstSeen 2026-04-29, lastSeen 2026-09-04, culprit `superset.mcp_service.server`. Unlike 7KA, verified the *exact* pinned `fastmcp==3.4.7` locally (matches superset-shell's requirements.txt exactly, no version-skew risk) before committing to this pick.

**Root cause** (full chain read from source, not guessed): `superset/mcp_service/server.py`'s tool-search-transform `call_tool` proxy has a guard clause (`if name in {call_tool_name, search_tool_name}: raise ToolError(...)`) with no `log_level` kwarg. `fastmcp.exceptions.FastMCPError.__init__` defaults `log_level=logging.ERROR`; FastMCP's own `call_tool` (`fastmcp/server/server.py`) does `logger.log(e.log_level, f"Error calling tool {name!r}")` on any `FastMCPError` — unconditionally ERROR for this exception, via FastMCP's *own* logger, before Superset's middleware layer is even reached. This directly contradicts Superset's own established policy: `mcp_service/middleware.py`'s `_USER_ERROR_TYPES`/`_is_user_error()` already classifies `ToolError` as an expected 400-class "user error" (agent misuse) that should log at WARNING and skip the Sentry-forwarding `MCP_ERROR_HOOK` — but that classification lives one layer too late to catch FastMCP's own internal log call. Confirmed via `preset/app.py::configure_sentry`: `LoggingIntegration(event_level=logging.ERROR)` promotes any ERROR-level log app-wide to Sentry, and there's already a precedent `ignore_logger("superset.mcp_service.middleware")` call there for exactly this class of "raw ERROR log would double-report a sanitized error" problem — just not extended to FastMCP's own logger (correctly so — that logger also carries genuine system-level tool failures, so blanket-ignoring it would hide real errors; the surgical fix is the per-exception `log_level` FastMCP already supports, not a logger-wide suppression).

**Fix**: add `log_level=logging.WARNING` to the one `ToolError(...)` call at that guard clause. No other `ToolError` site touched. No functional/behavior change — MCP response to the client is identical; only log severity (and thus Sentry-reachability) changes.
