**Picked: SUPERSET-PYTHON-NMA** — https://preset-inc.sentry.io/issues/5588396277/ — `UserLookupError: No access`, **10471 events, 31 users**, firstSeen 2024-07-09, lastSeen 2026-09-04, culprit `CurrentUserRestApi.get_me`.

**Root cause** (read from source across two repos, not guessed): `superset/views/users/api.py`'s `CurrentUserRestApi` (`get_me`/`get_my_roles`/`update_me`) all access `g.user` after `@protect()`/`@permission_name()`/`@safe`. Confirmed via `git show 1f5df7407f` (PR #36410, merged 2025-12-11) that this PR **removed** the three methods' manual `try/except NoAuthorizationError: return self.response_401()` guards, trusting `@protect()` to cover auth failures. It doesn't: read flask_appbuilder's actual installed `security/decorators.py::protect` — `wraps()` calls `verify_jwt_in_request()`/checks `current_user.is_authenticated` with zero exception handling of its own. And `UserLookupError` was **never** caught anywhere in this file, before or after #36410 — that gap predates the PR. Traced the exception's origin into `preset/security/manager.py` (preset-io/superset-shell repo, fetched fresh via `/tmp/blame-clones/preset-io__superset-shell`): `_upsert_user_jwt_user_info` raises `UserLookupError("No access")` when a validly-authenticated JWT belongs to a real workspace member who genuinely has no assigned role — Manager's "no access" sentinel, explicitly commented in that file as "the expected, routine path for those users, not a sync gap" (sc-115333 precedent, same family as the 08-04 `_get_preset_user` noise fix already in memory). Nothing catches this on the way up; it reaches flask_appbuilder's `@safe` decorator (confirmed via installed package source: `except Exception as e: log.exception(e); return self.response_500(...)`), producing a full-traceback ERROR log + generic 500 instead of a clean 401. Confirmed lastSeen (09-04) post-dates #36410 by 9 months — this is a live current-code bug, not deployment lag (ruled out the Y83/BBX-style stale-line false positive explicitly by checking commit dates line up).

**Established in-repo precedent for the fix**: `superset/views/base.py`'s `api` decorator (legacy MVC views) already does exactly the right thing — `except NoAuthorizationError: logger.warning(...); return json_error_response(..., status=401)`. Mirroring this into `CurrentUserRestApi`, extended to also catch `UserLookupError` (the exception actually observed).

This is higher-stakes than typical log-noise picks: it's not just Sentry cleanliness, it's real users (31 of them) getting a generic 500 instead of a clean 401 on `/api/v1/me/` when their workspace access is genuinely revoked — a behavior bug, not just observability.
