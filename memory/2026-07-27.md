### Picked: SUPERSET-PYTHON-P8F + SUPERSET-PYTHON-Y7R (one root cause, two Sentry issues)

- **Root cause** (confirmed by reading `superset/utils/slack.py` + `superset/reports/api.py` from a fresh `apache/superset` clone, and both full Sentry event bodies): a workspace's Slack bot token being invalid/revoked (`not_authed`/`invalid_auth`) is an expected multi-tenant config state, not a Superset bug. The request path already handles it correctly — `_get_channels()` catches `SlackApiError`, `get_channels_with_search()` wraps it as `SupersetException`, `slack_channels()` REST handler catches that and returns a correct 422 — but **both** intermediate catch blocks log at `logger.error` (one with `exc_info=True`, full traceback), so Sentry's `LoggingIntegration` (event_level=ERROR) captures both as separate issues on every occurrence. Same bug class as MANAGER-PYTHON-2ZF, MANAGER-PYTHON-374, SUPERSET-PYTHON-XVB/YYS (already-handled condition logged too loudly). Confirms the `should_use_v2_api()` function in the same file already sets precedent — it logs Slack auth/scope errors at WARNING, not ERROR.
- **Fix**: downgrade `logger.error` → `logger.warning` at both call sites (`superset/utils/slack.py::_get_channels`, `superset/reports/api.py::slack_channels`), dropping the traceback on the first. Log-severity-only, no behavior/response change.
