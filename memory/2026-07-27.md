### Picked: `superset/tasks/cron_util.py::cron_schedule_window()` — `CroniterBadDateError` crashes `reports.scheduler` for every active schedule
- **Root cause**: `superset/reports/schemas.py::validate_crontab()` validates crontab strings via `croniter.is_valid()`, which is purely syntactic. It returns `True` for cron expressions that can never match a real calendar date (e.g. `"0 0 30 2 *"` — Feb 30th, `"0 0 31 4 *"` — April 31st). Such a crontab passes API schema validation on report/alert create/update and saves as an active `ReportSchedule`.
- **Reachability confirmed**: the celery-beat task `reports.scheduler` (`superset/tasks/scheduler.py:88-99`) iterates every active schedule in an unguarded nested loop, calling `cron_schedule_window()` for each. Consuming `crons.all_next(datetime)` for a bad-date cron raises `croniter.CroniterBadDateError` on the very first `next()` — confirmed empirically in `/tmp/ss-test-venv`: `croniter('0 0 30 2 *', ...).all_next(datetime)` raises `CroniterBadDateError: failed to find next date`, uncaught anywhere in the chain (the celery task decorator's `autoretry_for=(Exception,)` just retries the whole task 3x against the same bad data, then fails it). Because the loop has no per-schedule isolation, **one** bad-but-syntactically-valid crontab crashes report/alert scheduling for **every** other active schedule across the whole instance (multi-tenant blast radius), on every beat tick — higher-impact than the typical single-request-500 shape of this pipeline's prior picks.
- **Hierarchy confirmed**: `CroniterBadDateError.__mro__` = `(CroniterBadDateError, CroniterError, ValueError, Exception, BaseException, object)`.
- **Fix shape differs intentionally from prior picks in this series**: this is a background celery-task loop, not an HTTP request/response path, so there's no 4xx/500 status to map to. Instead of a new `superset/exceptions.py` subclass, wrapped the `crons.all_next(datetime)` iteration in `try/except CroniterBadDateError`, logging loudly (`logger.error`, since the schedule can never fire until someone manually fixes it — not a graceful auto-recovery like the sibling case) and letting the generator end. This mirrors the existing sibling precedent a few lines above in the same function, which already catches `UnknownTimeZoneError` and falls back to UTC with `logger.warning`.
- Regression test `test_cron_schedule_window_invalid_cron_date` added to `tests/unit_tests/tasks/test_cron_util.py` (existing house-style parametrize file), covering both Feb 30th and April 31st, asserting `[]` returned instead of raising.
