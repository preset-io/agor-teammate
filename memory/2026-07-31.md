### Picked: SUPERSET-PYTHON-12EZ
235,727 events — by far the highest-volume unresolved issue in `preset-inc` (next highest is MANAGER-PYTHON-2ZF at 130k, already fixed/merged). Had been sitting as an unpicked candidate since first appearing in 07-22/07-23's candidate lists, apparently never actually root-caused by this pipeline before today.

**Root cause** (verified via full Sentry event + reading `superset/models/helpers.py`, `superset/common/query_context_processor.py`, `superset/charts/data/api.py`, `superset/views/error_handling.py`, `superset/exceptions.py`, `superset/jinja_context.py` — not guessed):

A customer virtual dataset template does an indexed lookup like `filter_values('col')[0]`; with no active dashboard filter for that column this is `[]` and Jinja raises `UndefinedError`. That's already correctly caught in `get_rendered_sql()` and converted to `QueryObjectValidationError` (400) — not a bug, not touched.

The actual leak: `QueryContextProcessor.get_df_payload()` calls `query_cache_key()` *before* its only try/except block (which just wraps `get_query_result`). When the template also uses a macro matched by `ExtraCache.regex` (`current_user_rls_rules`, `current_user_id`, `url_param`, etc.), `query_cache_key()` calls `get_extra_cache_keys()` → `get_sqla_query()` → `get_from_clause()` → `get_rendered_sql()` — all outside that try/except. Combined with `ChartDataRestApi.data()` not being `@handle_api_exception`-decorated, the resulting `QueryObjectValidationError` propagates fully uncaught to Flask's global `show_unexpected_exception` catch-all, which unconditionally `logger.exception()`s (ERROR + full traceback) and returns 500 — regardless of the exception's real 400 status. This isn't unique to this one exception type: any `SupersetException` subclass without its own specific `@app.errorhandler` (most of `superset/exceptions.py`'s validation types) hits the same catch-all.

**Checked for an existing in-flight fix first**: found PR apache/superset#42366 (superset-error-cleanup pipeline, not this one) touching the exact same `get_rendered_sql()` function — but on inspection its fix is redundant (`jinja2.exceptions.UndefinedError` is already a subclass of the `TemplateError` the pre-existing `except` clause catches, verified via `UndefinedError.__mro__`), and it doesn't address the actual Sentry-volume bug (the global-handler logging/status issue) at all. Proceeded with this as a genuinely separate, unclaimed root cause — different file, no conflict.

**Fix**: added `@app.errorhandler(SupersetException)` in `set_app_error_handlers()` (`superset/views/error_handling.py`), mirroring the existing `handle_api_exception` decorator's own `except SupersetException` branch — logs via `get_logger_from_status(ex.status)` (WARNING for 4xx) and returns `ex.status` instead of hardcoded ERROR/500. Verified Flask/Werkzeug dispatch is by MRO distance regardless of registration order, so subclasses with their own specific handler (`SupersetErrorException`, `SupersetErrorsException`, `CommandException`) are unaffected.

**Tradeoff disclosed in the PR**: HTTP status + log level change for previously-uncaught 4xx/404-status `SupersetException` subclasses (QueryObjectValidationError, AdvancedDataTypeResponseError, InvalidPostProcessingError, CacheLoadError, NoDataException, NullValueException, SupersetTemplateException, DatabaseNotFound, MissingUserContextException, QueryClauseValidationException, ScreenshotImageNotAvailableException) — now correctly return their real status instead of always 500/ERROR. 500-status subclasses unaffected (covered by a regression test).

### Picked: `superset/commands/report/base.py::validate_report_frequency` — uncaught `CroniterBadDateError`

**Root cause** (verified empirically, not guessed): `superset/reports/schemas.py::validate_crontab()` only calls `croniter.is_valid(str(value))` — purely syntactic, returns `True` for crontabs that can never produce a real calendar date (e.g. `"0 0 30 2 *"`, Feb 30th). Such a crontab passes schema validation and reaches `validate_report_frequency()`, which (only when `ALERT_MINIMUM_INTERVAL`/`REPORT_MINIMUM_INTERVAL` is configured >= 120s — the default is 0, so this only fires under a real but non-default operator config) calls `croniter(cron_schedule)` and iterates it with `next()`. Confirmed via standalone repro (own scratch venv, `croniter==6.2.4` matching the repo's `croniter>=6.2.2` pin): this raises `croniter.croniter.CroniterBadDateError` — MRO `(CroniterBadDateError, CroniterError, ValueError, Exception, BaseException, object)`, **not** a marshmallow `ValidationError` — so it propagates straight past both callers' `except ValidationError` (`CreateReportScheduleCommand.run()` and `UpdateReportScheduleCommand.run()`), surfacing as an opaque 500 instead of the intended 422.

Same underlying croniter behavior as the 07-27 Sentry-burndown fix (PR #42486, `tasks/cron_util.py::cron_schedule_window()`), but a genuinely different site: that one is the celery-beat scheduler background task (catch+log+skip is correct there); this one is synchronous API-layer validation during report/alert create/update, where the correct fix is a proper marshmallow validation error, not a silent skip. Confirmed no existing exception class fit (`superset/commands/report/exceptions.py` has no "invalid crontab date" class); followed the file's own established pattern (`ReportScheduleFrequencyNotAllowed` a few classes above, same shape) for the new one rather than inventing a new style.

**Fix**: added `ReportScheduleCrontabNotValidError(ValidationError)` (field_name="crontab") to `superset/commands/report/exceptions.py`; wrapped the croniter iteration in `validate_report_frequency` in `try/except CroniterBadDateError`, raising the new error `from ex`. Regression test (`test_validate_report_frequency_never_matching_crontab`, parametrized over both report types) added to `tests/unit_tests/commands/report/base_test.py`, matching the file's existing `app_custom_config` decorator pattern.
