Picked over the low-volume customer-noise MCP singletons for being a clean, well-evidenced, code-fixable pair with real diagnostic value (the current behavior hides the true error).

**Root cause, verified against `origin/master@fcb5e51a`, not guessed:**
1. `preset/managers/permission.py::_do_send_dar_permission_workspace_event` rebuilds a DAR event's user list by calling `self._user_manager.find_user_by_username_cached(grantee.grantee_identifier)` for each USER grantee still on the permission, then reads `u.username` with **no None-check**. `find_user_by_username_cached` (`preset/managers/user.py:397`) returns `None` when the username doesn't resolve to an existing `PresetUser` row — an expected, documented return value (its own body does `if user: ...; return user`). Any stale/deleted-user grantee reference left on an existing permission crashes this with `AttributeError` → **MANAGER-PYTHON-43X**.
2. **Known-but-unpropagated pattern**: the sibling method `_build_dar_permission_grantees` (create-path validator, line ~1878) already guards the identical call — `if not user: raise PermissionGranteeNotExistException`. `_do_send_dar_permission_workspace_event` (background re-sync of an *existing* permission, called from 3 sites incl. `remove_grantee_from_permissions`) never got the equivalent treatment; the correct behavior here is skip-and-warn, not reject, since it's not validating new input.
3. The AttributeError propagates via that method's own `except Exception: logger.exception(...); self.session.rollback(); raise` up through `remove_grantee_from_permissions` → `manager_resource_event_dispatcher.on_user_removed_from_workspace` → into `preset/managers/user.py::remove_user_from_team`'s except block: `logger.exception("Failed to remove user:%s from team:", user_id, team_id)` — **one `%s` placeholder, two positional args**. Python's logging `getMessage()` raises `TypeError: not all arguments converted during string formatting` *before* the next line's `self.session.rollback()` runs — so the rollback is skipped and the TypeError (not the real AttributeError) is what actually reaches the client as the 500, masking the true error → **MANAGER-PYTHON-43Y**.

**Fix scope**: (a) guard the grantee lookup in `_do_send_dar_permission_workspace_event` — skip + warn on a `None` user instead of crashing; (b) fix the broken format string in `remove_user_from_team` so the exception handler doesn't itself crash and skip rollback. Both `Fixes` refs go in one commit (one incident, two Sentry fingerprints) — disclosed as a deliberate exception to "one issue per run" since they're the same causal chain, not unrelated scope creep.
