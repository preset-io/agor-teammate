### Root cause (confirmed via source + both full Sentry stacktraces, not guessed)
`BaseSSHTunnelForwarderError` (raised from `Database.get_sqla_engine()` in `superset/models/core.py`) isn't a `SupersetException` subtype, so no specific handler catches it. It falls into one of **two different** ERROR-level catch-alls in `superset/views/error_handling.py`, depending on whether the endpoint uses `@handle_api_exception`:
1. `handle_api_exception.wraps`'s final broad `except Exception` — confirmed via T7B's stacktrace (`error_handling.py:100 wraps` frame present). `DashboardRestApi.get_datasets` is `@handle_api_exception`-decorated.
2. The global Flask `@app.errorhandler(Exception)` handler `show_unexpected_exception` — confirmed via YY5's stacktrace having **no** `error_handling.py` frame at all (propagated past `ChartDataRestApi.data`, which has no `@handle_api_exception` decorator, all the way to the global handler). That handler double-logs at ERROR (`logger.warning(exc_info=True)` + `logger.exception`).

Checked `superset/commands/database/ssh_tunnel/exceptions.py` — only covers config-time validation (creating/updating a DB's SSH tunnel settings), nothing for query-time connection failures. Reused existing `SupersetErrorType.CONNECTION_HOST_DOWN_ERROR` (already used for "host might be down" DB errors in `db_engine_specs/postgres.py` etc.) rather than adding a new error type for one call site.

### Fix
Added a shared `handle_ssh_tunnel_error()` helper in `superset/views/error_handling.py`: logs at WARNING (not ERROR), returns a structured `SupersetError` (`CONNECTION_HOST_DOWN_ERROR`, HTTP 400) instead of the opaque 500. Wired into **both** catch-all sites so it covers decorated and non-decorated endpoints alike — a single-site fix would have only silenced one of the two Sentry issues.

**Tradeoff explicitly disclosed in the PR**: HTTP status changes 500→400 for these two failure modes — a real behavior change for any API client checking status codes, even though 400 is more correct. No raise→suppress semantics change otherwise.

### Learnings
- On clone-mode Agor branches, `git push -u origin <branch>` can report success (and even print "branch set up to track") without actually creating a usable local remote-tracking ref, because the repo's fetch refspec may be narrowed to just the default branch. `gh pr create` then fails claiming the branch isn't pushed. Fix: pass `gh pr create --head <branch> --base <base>` explicitly rather than relying on ambient detection — confirmed the branch existed on origin via `git ls-remote --heads origin <branch>` before doing so.
- `agor_execute_tool` still occasionally throws a transient "claude-sonnet-5 is temporarily unavailable" classifier error on plain `git push` calls (same as the 07-27 learning, now also seen on git/gh commands, not just `agor_execute_tool` itself) — retrying immediately succeeded both times.
