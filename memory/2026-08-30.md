### Picked: `SUPERSET-PYTHON-95B` — unretryable 403 logged as unhandled ERROR in `push_workspace_update` Celery task

**preset-io/superset-shell.** 10,314 events all-time, chronic since 2023-05-09, 0 users, still firing weekly (lastSeen 2026-08-27). `multi_tenant.push_workspace_update` (`preset/tasks.py`) is a Celery task decorated `autoretry_for=(Exception,), max_retries=5, retry_backoff=True` — it retries *every* exception, including non-transient ones. It calls `push_workspace_status_update()` (`preset/multi_tenant/workspace_pub_sub.py`), which POSTs to Manager's `/status-updates/` endpoint via the internal client; the client's `raise_for_status()` lets `requests.exceptions.HTTPError` propagate completely unhandled. A 403 (permission/auth denial) is not retryable — 5 backed-off retries always fail identically, then Sentry captures the final attempt as an unhandled ERROR (mechanism: celery, handled: false). Breadcrumbs show a JWKS refresh immediately before the failing POST, consistent with a workspace-teardown auth race, not malformed input.

Found a direct precedent **in the same file**: `poll_workspace_events()` already catches `HTTPError`, checks `e.response.status_code == 404`, and logs a WARNING instead of raising. Directed the implementation session to apply the identical idiom to `push_workspace_status_update()` for `403`, re-raising unchanged for any other status code.

**Tradeoff disclosed in PR**: failure-mode semantics change for 403s specifically — unhandled ERROR-after-5-retries → single-attempt WARNING-no-retry. Functional outcome unchanged (status push still dropped either way, since retrying a 403 can't succeed); this only makes it faster and quieter, matching the codebase's own precedent for the sibling 404 case.
