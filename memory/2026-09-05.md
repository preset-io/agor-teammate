### Root cause (verified against `preset-io/manager` master source via `gh api`, not guessed)

Both trace to the same block in `preset/middleware/cord_client.py::handle_requests_exceptions` (the shared decorator wrapping every `CordClient` method that talks to the third-party Cord SaaS, `api-cord.app.preset.io`): the `except requests.exceptions.HTTPError` handler's `if status_code >= 500:` branch calls `logger.exception(...)` (ERROR + full traceback) before raising `CordClientHTTPFatalException`. Confirmed the Sentry-captured exception type (`HTTPError`, not `CordClientHTTPFatalException`) and message match this exact `logger.exception` call verbatim — it's the log call, not the raise, that Sentry's logging integration captures.

The calling job (`preset/jobs/cord_sync_user_group_memberships.py`) already wraps the sync in `@job_extension(..., autoretry_for=(Exception,), retry_backoff=True, retry_backoff_max=300, max_retries=10, final_exception_class=CordDeadLetterException)` — Celery retries up to 10x with backoff, and only once retries are exhausted does the job's own `except CordDeadLetterException` block fire its own (correct, appropriately-scoped) `logger.exception` with full context. The decorator's per-attempt `logger.exception` fires on *every* transient 5xx, including attempts that succeed on retry seconds later — pure noise duplicating what the dead-letter handler already reports on genuine terminal failure. The decorator already treats 400/422, 409, and 401/403 this way correctly (`logger.warning`); only the `>=500` branch uses `.exception`. Direct in-repo precedent for this exact noise class: PR #3850 (`fix(cord): treat Cord 409 conflicts as already-synced`, sc-112882) — same file, same decorator, prior SRE-motivated Cord-noise fix. `gh search prs`/`gh pr list --search cord` across preset-io/manager confirmed no open/merged PR touches the `>=500` branch specifically.

### Fix (delegated, pure log-level change, no behavior/exception-type change)

Downgrade the one `logger.exception` → `logger.warning` in the `>=500` branch only (leaving the final catch-all `else`, the other status-code branches, `ConnectionError` handling, and the job's own dead-letter handler untouched). `CordClientHTTPFatalException` is still raised identically; Celery retry/backoff/dead-letter behavior is completely unaffected — only Sentry/log noise drops.
