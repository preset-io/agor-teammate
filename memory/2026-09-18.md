- SQLAlchemy's base compiler (`visit_like_op_binary`) always renders a literal `ESCAPE '<char>'` clause when `.like(..., escape=...)` is used. Checked `sqlalchemy_bigquery.base.BigQueryCompiler` (installed in `/home/agorpg/tmp/ss-venv`) — it overrides `visit_contains_op_binary`/`visit_startswith_op_binary`/`visit_endswith_op_binary` (via `_maybe_reescape`, which swaps wildcard-escaping to BigQuery's backslash convention) but does **not** override `visit_like_op_binary`/`visit_not_like_op_binary`. So the raw `ESCAPE '!'` leaks straight into the GoogleSQL sent to BigQuery, which has no ESCAPE keyword on LIKE.
- Reproduced standalone: compiled `sa.func.lower(t.c.col).like('%foo%', escape='!')` against `BigQueryDialect()` in the venv → `... LIKE '%%foo%%' ESCAPE '!'`, confirming the exact syntax error shape.
- Verified the fix compiles clean: `sa.func.lower(expr).contains(search.lower(), autoescape=True)` — `.contains()` **is** covered by BigQueryCompiler's override, so BigQuery gets backslash-escaping with no ESCAPE clause, while Postgres/MySQL/sqlite keep a correct dialect-native `LIKE ... ESCAPE` clause (spot-checked all three).
- `LIKE_ESCAPE_CHAR`/`escape_like_pattern()` have no other callers (grepped the whole repo) — dead code once `build_like_predicate` stops using them; had the implementation session delete both.
