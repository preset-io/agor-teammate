**Root cause** (verified against current `preset-io/superset-shell` master, not guessed): `SupersetShellSecurityManager.upsert_groups()` (`preset/security/manager.py`) does check-then-insert (`find_groups()` then `add_all()`+`commit()`) with **zero exception handling** around the commit. Two concurrent JIT logins for users sharing a not-yet-synced group can both see it missing and both INSERT — the loser hits `IntegrityError` (`UniqueViolation` on `ab_group_name_key`, culprit shows as `DashboardRestApi.favorite_status` because that's the incidental endpoint the losing request was serving), propagating uncaught and leaving the SQLAlchemy session broken for the rest of the request — producing 178E's cascading `PendingRollbackError` on the next query in the same request. Confirmed via `git log origin/master -L` that this function has had this exact unguarded shape since introduction (PR #2926, 2025-04-01) — a live bug, not the deployment-lag/stale-build pattern that's dominated recent runs (Y83/BBX/ZX7/md5/appbuilder.app family). Found an exact in-file fix precedent: `upsert_user()` (same file, ~line 1448) already catches `(StaleDataError, IntegrityError)` on the identical race, rolls back, and re-queries — mirrored that shape for `upsert_groups()`. Test precedent found too: `test_upsert_user_integrity_error_handling` in `tests/preset/security/test_manager.py`.
