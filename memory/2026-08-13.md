## Sentry MCP auth outage — RESOLVED, direct-API bypass shipped (root cause + fix)

Picked up the standing "Sentry MCP auth blocked" issue ([[project_sentry_mcp_auth_blocked]], blocked 08-10 through today) at Elizabeth's request, after she reported hitting a concrete OAuth error while trying to re-authorize interactively: `"Authorization server does not advertise the required callback issuer parameter"`.

### Root cause identified (not just re-confirmed the outage)
This is a client/server OAuth metadata mismatch, not a credentials or Sentry-account-permissions issue: Claude Code's MCP OAuth client enforces RFC 9207 / MCP SEP-2468 (expects an `iss` issuer parameter, or `authorization_response_iss_parameter_supported` advertised, on the OAuth callback to guard against mix-up attacks). Sentry's authorization server (`mcp.sentry.dev`) doesn't advertise that, so the client rejects the callback before a token is ever issued. Confirmed via web research (RFC 9207 spec, MCP SEP-2468, related `anthropics/claude-code` OAuth issues) rather than guessing — no exact prior report of this precise error string against Sentry specifically, so flagged as worth a fresh GitHub issue if an interactive `claude update` doesn't happen to have picked up a fix.

### Fix: bypass MCP OAuth with a direct REST API token, same pattern as Datadog
Per [[feedback_datadog_use_direct_api]]'s existing precedent (never use the Datadog MCP, curl the REST API directly with a key pair) — proposed and implemented the same approach for Sentry:

1. Elizabeth created a Sentry **Internal Integration** (org `preset-inc`) with read-only scopes (`project:read`, `org:read`, `event:read`). Note: Sentry's UI initially surfaced a "Client Secret" — that's the OAuth Client ID/Secret pair from a *Public Integration*, not usable as a static Bearer token; the correct credential is the token under an *Internal Integration's* "Tokens" section. Flagged this distinction before she went further, to avoid setting up the wrong integration type.
2. She set the resulting token as `SENTRY_API_TOKEN` in the workspace env (same mechanism `DD_API_KEY`/`DD_APP_KEY` already use) — never had the raw token pasted into the session transcript.
3. Verified live: `GET /api/0/organizations/preset-inc/` → 200, confirmed `access: [project:read, org:read, event:read]` exactly as configured.
