### Found the actual gap: `security_manager.raise_for_access(query=...)` itself can leak `TemplateError`, and one call-site family never got the memo
Traced *why* `Query.raise_for_access()` needs a `TemplateError` catch at all: `security_manager.raise_for_access(query=...)` (`superset/security/manager.py:4403`, the `query`/`table` branch) calls `process_jinja_sql()` (`superset/sql/parse.py:2522`) unguarded — that function's own docstring states `:raises jinja2.exceptions.TemplateError: If the Jinjafied SQL could not be rendered`. So *every* caller of `security_manager.raise_for_access(query=...)` is exposed, not just the SQL Lab export family.

Grepped all `raise_for_access` call sites. Found the exact sibling-drift pair:
- **Already fixed, and the actual origin of the fix pattern**: `superset/explore/utils.py::check_query_access()` (pre-existing, not from today) calls `security_manager.raise_for_access(query=query, allow_query_authorship_bypass=True)` wrapped in `try/except TemplateError as ex: raise SupersetTemplateException(str(ex)) from ex`, with an explicit comment: "raise_for_access() Jinja-renders the query's SQL to resolve the tables it touches; a malformed template surfaces here as a raw jinja2 exception rather than a Superset one." This is the textbook precedent this skill looks for.
- **Not fixed**: `superset/common/query_context_processor.py::QueryContextProcessor.raise_for_access()` (line ~908-921) calls the *identical* `security_manager.raise_for_access(query=self._qc_datasource)` when `self._qc_datasource.type == DatasourceType.QUERY`, with **zero exception handling**.
