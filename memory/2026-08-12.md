### Candidate re-verified against current `origin/master`, refined from 08-11's pick
08-11 found `superset/security/manager.py::raise_for_access()` calling `superset/sql/parse.py::process_jinja_sql()` (whose own docstring documents `:raises jinja2.exceptions.TemplateError:`) with no try/except anywhere in either function, and deferred implementing because apache/superset#42928 was actively rewriting that same function body.

- **#42928 has since merged** (`gh pr view 42928`: `state: MERGED`, `updatedAt: 2026-08-12T02:35:46Z`). Re-pulled current `superset/sql/parse.py` and `superset/security/manager.py` from `origin/master` (raw GitHub content, since the shared local clone's pytest env is broken per [[project_superset_shared_repo_pytest_env_broken]]): the `#42928` rewrite touched `process_jinja_sql()` extensively (added `SupersetParseError` for unresolvable partition macros) but did **not** touch the raw `processor.env.parse(sql)` call — the docstring's undocumented-as-a-problem `TemplateError` raise survives the rewrite untouched. `raise_for_access()` (now noqa: C901, `security/manager.py:3894`) still has zero try/except around its `process_jinja_sql(...)` call (`~line 4045`). Confirmed by reading the full function body (grep for `try:`/`except`/`raise` between lines 3894–4150 in the pulled file): the only raises in the function are its own `SupersetSecurityException`s: nothing wraps the parse call.
- **Refined the fix location** — patching `raise_for_access()` itself is not the right surgical fix: it's a 250-line, `noqa: C901` function called from ~50+ sites across the codebase with varying parameter combinations (`table=`, `query=`, `sql=+database=`, etc.), and only the `query=`/`sql=+database=` branch reaches `process_jinja_sql` at all. Widening exception handling inside that shared function risks changing behavior for unrelated callers. Instead, traced *every* call site that can reach the `process_jinja_sql`-triggering branch (`sql=`+`database=`, or `query=` a `Query`-like object) and checked which already guard against `TemplateError`:
  - `superset/sqllab/api.py` (`~line 262`, SQL-format endpoint) — **already catches** `except TemplateError as ex: raise SupersetErrorException(..., error_type=GENERIC_COMMAND_ERROR, status=400) from ex`.
  - `superset/commands/sql_lab/estimate.py` (already fixed via this pipeline, #42757) — **same pattern**, confirmed still present post-#42928.
  - `superset/commands/sql_lab/results.py::SqlExecutionResultsCommand.validate()` (`~line 75`) — `self._query.raise_for_access()` wrapped only in `except SupersetSecurityException as ex: raise SupersetErrorException(..., status=403)`. **No `TemplateError` catch.**
  - `superset/commands/sql_lab/export.py::SqlResultExportCommand.validate()` — **identical** try/except shape, same gap.
  - `superset/commands/sql_lab/streaming_export_command.py::SqlResultStreamingExportCommand.validate()` — **identical** try/except shape, same gap.
  
  This is textbook sibling-site drift (skill's #1 pattern): the exact same guard exists twice already in this SQL Lab subsystem, and three sibling command files copy-pasted the same `try/except SupersetSecurityException` block without it. `Query.raise_for_access()` (`superset/models/sql_lab.py:326`, `security_manager.raise_for_access(query=self, force_dataset_match=True)`) re-parses `query.sql` (raw, unrendered Jinja) via `process_jinja_sql` whenever `executed_sql` isn't yet set on the `Query` row — e.g. a SQL Lab async query with malformed Jinja (unclosed `{% if %}`) that fails during execution before `executed_sql` is persisted; a client polling `/api/v1/sqllab/results/` (`results.py`), or hitting CSV export (`export.py`) / streaming CSV export (`streaming_export_command.py`) for that same query, hits the unguarded re-authorization parse and gets a raw 500 instead of a typed 4xx.
- **Empirically verified the exception**: `python3 -c "import jinja2; jinja2.Environment().parse('{% if x %}')"` raises `jinja2.exceptions.TemplateSyntaxError`, confirmed via `TemplateSyntaxError.__mro__` to be a `TemplateError` subclass — matches the docstring's documented (but here, unhandled) raise exactly.
