**Picked: SUPERSET-PYTHON-179V** — https://preset-inc.sentry.io/issues/7741055103/ — `TypeError: Cursor.execute() got an unexpected keyword argument 'async'`, culprit `DatabaseRestApi.table_extra_metadata`, 1 event (2026-09-18), but the mechanism fires on every table-metadata fetch for the affected connection (not a one-off).

**Root cause, verified via source (not guessed):** traced `databases/api.py:table_extra_metadata` → `presto.py:get_extra_table_metadata` → `presto.py:get_create_view` → `hive.py:execute` → `databricks/sql/telemetry/latency_logger.py:wrapper`. Downloaded and read the actual pinned dependencies: `pyhive.hive.Cursor.execute(operation, parameters=None, **kwargs)` happily swallows an `async` kwarg (confirmed by reading PyHive 0.7.0 source) — so a real pyhive-backed connection never hits this. But `databricks.sql.client.Cursor.execute()` (databricks-sql-connector 4.5.0, the real official connector) has a **fixed signature with no `**kwargs`** — passing `async=False` raises exactly this TypeError. `HiveEngineSpec.execute()` (hive.py) unconditionally does `cursor.execute(query, **{"async": async_})`, assuming a pyhive cursor.

The only way a `databricks.sql` cursor reaches `HiveEngineSpec.execute()` is via `DatabricksHiveEngineSpec` (databricks.py, `drivers={"pyhive"}`) being selected as the engine spec for a connection that's actually backed by the real databricks-sql-connector. Root cause: `get_engine_spec(backend, driver)` (`db_engine_specs/__init__.py`) explicitly falls back to "the first DB engine spec that supports the backend" (module-definition order, own docstring calls this "a random DB engine spec") whenever the stored SQLAlchemy URI's driver string doesn't exactly match any registered `drivers` key. For `engine="databricks"`, `DatabricksHiveEngineSpec` is defined FIRST among the 4 concrete specs in databricks.py (Hive/pyhive, ODBC/pyodbc, Native/connector, PythonConnector/databricks-sql-python — the last being the modern/"Recommended" one). Any Databricks `Database` row with an unrecognized/legacy driver suffix silently gets treated as a pyhive Interactive-Cluster connection while actually connecting via the real connector — crashing the instant any Presto/Hive-inherited metadata method runs.

**Corroborating precedent found during root-causing:** apache/superset#24786 (2024, "Hive `async` kwarg unexpected keyword when connecting to Databricks Unity Catalog") is the identical crash via a different call path (SQL Lab query execution, bare `databricks://` URI). The obvious naive fix (PR #24984, strip the `async` kwarg from `HiveEngineSpec.execute` entirely) was **closed unmerged** — would break real pyhive/Presto async-cancellation semantics. Also checked `tests/unit_tests/db_engine_specs/test_presto.py::test_get_create_view_propagates_other_errors` — an existing, deliberate test asserting non-`DatabaseError` exceptions must propagate out of `get_create_view` (not be silently swallowed as "not a view"). This ruled out my first instinct (widen the except clause in `get_create_view` to also catch `TypeError`) — that would violate an intentional existing contract, not fix the actual bug. Glad I checked before implementing.

**Fix shipped (surgical, single file):** reorder `superset/db_engine_specs/databricks.py` so `DatabricksPythonConnectorEngineSpec` is defined before `DatabricksHiveEngineSpec` (pure relocation of the ~16-line Hive spec class to the end of the file, no logic changes) — the ambiguous-driver fallback in `get_engine_spec` now prefers the modern general-purpose connector spec over the legacy Interactive-Cluster one. Comment added documenting the non-obvious file-order invariant for future editors. Did NOT touch `HiveEngineSpec.execute()` or `get_create_view`'s exception handling — that's the correct boundary given the #24786/#24984 precedent and the existing propagation test.
