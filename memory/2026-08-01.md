### Picked: `SUPERSET-PYTHON-WDZ` — `SqlLabException: Failed at getting query`
30,500 occurrences, 24 users impacted, first seen 2025-04-05, still firing daily — new to this pipeline's skip-list, not previously triaged.

**Root cause** (verified empirically, not guessed): `superset/sql_lab.py::get_query` is wrapped in `backoff.on_exception(SqlLabException, interval=1, max_tries=5)`. Its `except` block catches any exception from the ORM lookup and wraps it as `SqlLabException`, but never calls `db.session.rollback()`. The Sentry event's exception chain shows a SQLAlchemy `PendingRollbackError` ("...first issue Session.rollback()") chained under an `OperationalError`/`QueryCanceled` (dropped connection / statement timeout). Once a session enters this state, SQLAlchemy blocks *any* further operation on it until `.rollback()` is called — so every one of the 5 backoff retries reused the same poisoned session and failed identically. The retry loop was structurally guaranteed to burn all 5 attempts and give up, with zero chance to recover from what may have been a transient connection blip.

Verified via a standalone repro (own scratch venv, `sqlalchemy==1.4.54` matching the repo's pin, in-memory sqlite): poisoned a session via a failed flush, then called a `get_query`-shaped function under the identical `backoff.on_exception` decorator. Without a rollback, all 5 retries failed identically with `PendingRollbackError`; adding `session.rollback()` in the except block let the very next retry succeed. Also traced the Flask-SQLAlchemy 2.5.1 (pinned) session-scoping mechanism directly from the wheel source to rule out an alternative "session leaks across celery tasks" hypothesis — Flask-SQLAlchemy registers its own `teardown_appcontext` hook that calls `session.remove()` unconditionally, so that path already self-heals; the real, narrower bug is purely within a single task's own retry loop.

**Fix**: added `db.session.rollback()` in `get_query`'s except block before re-raising `SqlLabException`. Pure reliability fix — no change to what's raised/logged, no change to `execute_query`/`execute_sql_statements`/`handle_query_error`, no change to backoff parameters. Added `test_get_query_rolls_back_session_before_retrying` to `tests/unit_tests/sql_lab_test.py` (mocks the ORM call to fail once then succeed, asserts recovery + that rollback() was called).
