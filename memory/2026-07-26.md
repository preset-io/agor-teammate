### Picked: SUPERSET-PYTHON-XVB + SUPERSET-PYTHON-YYS (one root cause, two Sentry issues)
Both are new — first appearance in this burndown's history.

**Root cause** (`superset/mcp_service/`, the `/mcp` FastMCP service): the third-party `mcp` SDK (v1.28.1) logs an MCP client mid-request disconnect (`starlette.requests.ClientDisconnect`, raised from `await request.body()` — a normal cancelled/timed-out tool call, not a Superset bug, 0 users impacted on both issues) at ERROR with a full traceback, **twice**, from a single incident:
1. `mcp/server/streamable_http.py:_handle_post_request`'s outer `except Exception as err` (~line 645) does `logger.exception("Error handling POST request")` on logger `mcp.server.streamable_http` → **SUPERSET-PYTHON-XVB** (2413 events, firing since 2025-10-16).
2. That same except block also does `await writer.send(Exception(err))`, pushing a bare-rewrapped exception onto the session's read stream; `mcp/server/lowlevel/server.py:_handle_message`'s `case Exception(): logger.error(f"Received exception from stream: {message}")` (logger `mcp.server.lowlevel.server`) logs it again → **SUPERSET-PYTHON-YYS** (2428 events, firing since 2026-01-18). `ClientDisconnect` always raises with zero args → `str()` is always `''` → this log line is always the literal `"Received exception from stream: "` (matches the actual empty-suffix Sentry event text).

Confirmed both issues share the identical root incident: sampled events for each carry the same trace_id/request_id/session_id. Verified by reading the actual installed `mcp` 1.28.1 source (`/home/kamil/.local/lib/python3.11/site-packages/mcp/server/{streamable_http.py,lowlevel/server.py}`), not just Sentry's stack trace — confirmed `writer.send(Exception(err))` is the *only* place an Exception is pushed onto that stream in this SDK version, and confirmed `ClientDisconnect.__str__()` is empty via `starlette/requests.py`/`responses.py` source.

Same bug class as the existing `FastMCPValidationFilter` already in `superset/mcp_service/server.py` (downgrades FastMCP's own "Error validating tool" ERROR logs to WARNING for the same reason — third-party SDK logging expected client conditions too loudly, dev polluting Sentry via LoggingIntegration's default `event_level=ERROR`).

**Fix**: new `logging.Filter` in `superset/mcp_service/server.py`, registered in `configure_logging()` next to `FastMCPValidationFilter`, downgrading ERROR→WARNING only for: (a) `mcp.server.streamable_http` records whose `exc_info` type is `ClientDisconnect` (precise, type info still present at that log site), and (b) `mcp.server.lowlevel.server` records whose message is the exact literal `"Received exception from stream: "` (type info is lost by that point — SDK rewraps in a bare `Exception()` — so matched on the literal empty-suffix signature instead). No other messages on either logger touched.
