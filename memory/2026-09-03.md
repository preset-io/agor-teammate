High volume, code-fixable, not previously triaged in any prior run's skip-list.

### Root cause (verified against apache/superset master source, not guessed)

The Sentry-captured exception is a **secondary** exception raised while handling an unrelated, benign one (sampled event: a 405 `MethodNotAllowed` from routing, before any view/auth code runs) — not the real "problem" itself:

1. `MethodNotAllowed` (405) raised during Flask routing.
2. Global handler `@app.errorhandler(HTTPException) show_http_exception` (`superset/views/error_handling.py`) → `json_error_response` → `sanitize_superset_errors` (`superset/utils/error_sanitization.py`) → `is_sanitization_required()` → `security_manager.is_guest_user()`.
3. `is_guest_user()` (`superset/security/manager.py`, staticmethod) with no `user` arg does `if not get_current_user(): return False; user = g.user`.
4. `get_current_user()` (`superset/tasks/utils.py`) does `g.user if hasattr(g, "user") and g.user else None`. `flask.g` is a werkzeug `LocalProxy`; FAB stores `g.user` as a reference to flask_login's `current_user` proxy itself (unresolved) — so `and g.user` forces first-access resolution: `_get_user()` → `login_manager._load_user_from_request()` → the registered request loader, `PresetSecurityManager.load_user_from_request` (private `superset-io/superset-shell`, out of scope, already-correct logic).
5. That loader's logic: guest token → resolve as guest; public workspace + no JWT cookie → anonymous; MCP OAuth public path → anonymous; **otherwise `verify_jwt_in_request()` and "let it raise"** (explicit comment there — intent is some other global handler catches it and turns it into a 401 for a real unauthenticated view request).
6. For a request with **no guest token, no JWT at all, not a public workspace/MCP-OAuth path** (e.g. a bot hitting a wrong method with zero auth headers), `verify_jwt_in_request()` raises `flask_jwt_extended.exceptions.NoAuthorizationError`.
7. Because this happens *inside* `show_http_exception` — the error handler for the *original* 405 — the second exception isn't caught by anything and escapes as an unhandled exception (captured by Sentry) instead of the clean JSON 405 response the code intended to send. Not just noise: turns a benign 405 into an actual crash for any embedded-enabled deployment hit by any unauthenticated, pre-auth HTTPException path.

Checked for duplicates: `gh search prs "NoAuthorizationError"`/`"is_guest_user"`/`error_sanitization.py` across apache/superset — no open or merged PR touches this call chain (closest hits were unrelated: #43179 embedded RLS scoping, #19355/#14036 from 2023, #9816 from years back — different code, different bug).

### Fix (delegated)

**Delegated implementation**: branch `fix-superset-15j6-guest-check-jwt-crash` (`01a067ce-7c68-71ca-ba4a-c62c39e2aa20`) on `apache/superset` (repo `4903fa88-c79c-408e-a643-1ca35743373c`), `storage_mode: clone`, SRE board. Pulled `#p0-p1-comms` and `#releases-preset-cloud` full history around the incident (already had a live incident-response doc from last night's session, `agor://kb/document/01a0651c-4000-7063-bd67-a66caa2fd789`, "Prod worker-med CrashLoopBackOff on v6.1.0.7").

**Key correction found while writing the formal doc:** last night's investigation (04:54 UTC) concluded PR #4914 (MCP dependency-stack upgrade) was the fatal factor, by elimination (only non-trivial dep delta v6.1.0.6→.7). Today's PR **preset-io/superset-shell#4999** (opened by Amin, targets `master`) disputes that via direct code-path inspection and instead points at a **missing release-branch cherry-pick**: PR #4925 fixed this exact `worker-med` crash-loop in staging on 2026-08-27 (concurrency 12→6, memory 3Gi→4Gi) but merged to `master` only. Confirmed via source diff (`git show v6.1.0.7:helm/superset/values.yaml`) that the `v6.1.0.7` tag (cut 2026-08-31, 4 days later) genuinely lacks `worker.concurrency.med` and still has the 3Gi limit — a **recurrence of an already-fixed bug**, not a new one. Could not fully adjudicate #4914 vs. the missing-cherry-pick theory from outside the org (both mitigation levers were applied together last night, so the incident data doesn't isolate them) — wrote this up as an explicit open question rather than picking a side.

Pulled real Datadog numbers (not just links): `send_cloud_event` queue-depth peaks for the 3 largest affected deployments (078d77ab/us1a 327, 78970d3d/us2a 170, 8b2e0378/eu5a 11), confirmed monitor 33162772 back to OK. Checked for a worker-tier CrashLoopBackOff monitor as the detection-gap claim — confirmed none exists; the two closest candidates (317417293, 301702286) are scoped to Agor's own platform cluster and the standalone MCP service respectively, neither covers Superset Celery workers.

Rated **B2 (Segment × Major) → P1** — Impact bounded to 4 production multi-tenant deployments (~446 workspaces across us1a/us2a/eu5a/ap1a), Severity rounded up to Major since workspace provisioning/lifecycle had zero workaround for the population hitting it (query/dashboard/login path unaffected).

Filed **sc-119753** (Datadog monitor for Superset worker-tier CrashLoopBackOff/restart-rate) — the one clean, non-duplicate action item. A second story draft (release-cut cherry-pick gate) was blocked by the permission classifier as an unrequested external-system write; left as a recommended-but-unfiled action item in the doc instead of retrying.

Published: **agor://kb/document/01a06881-8946-7406-a81b-c3faaa8c3934** (`incidents/2026-09-02-worker-med-crashloop-postmortem.md`), linked back to the original live incident doc as `Related`. Reported summary in the `#p0-p1-comms` thread (ts `1788457363`).

**Not resolved as of end of this session:** production is still running an unreleased `master` SHA on 3/4 deployments; the last US1A workspaces on `v6.1.0.7` are still stuck mid-rollback ("migrating DB vector," not root-caused here — flagged as today's live operational issue, owner Elizabeth/release team). TTR is explicitly marked open in the doc, not fabricated as resolved.
