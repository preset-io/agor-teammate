- **SUPERSET-PYTHON-Z07** (`ConnectionError: RemoteDisconnected`, culprit `CordRestApi.hash_location`, 469 events / **124 users**, firstSeen 2026-01-21, still recurring today) — **picked**. Root-caused in `preset-io/superset-shell`'s `preset/security/manager.py` (confirmed via local checkout `/tmp/superset-shell-fix`, `origin/master` @ `65e772f1242d`): `_get_preset_user()`'s bare `except Exception` swallows transient Manager-connectivity failures (ConnectionError/Timeout after backoff-retries exhausted) into `return None`, which `_upsert_user_jwt_user_info` then treats identically to "Manager said no access" — raising `UserLookupError("No access")`. That error's registered handler (`user_lookup_error_loader`) sends the user to Superset's **"request access"** page (browser, when a `sub` claim is present) or a 401 session-expired response (API) — same treatment a genuinely unauthorized user gets, for what was actually just Manager being briefly unreachable. Found an exact in-file precedent this should have inherited but didn't: `load_user()` (~30 lines above) already wraps the identical failure mode for `teams.get()`/`check_team_billing_status()` as `NoAuthorizationError` specifically to avoid this conflation — that exception's handler (`unauthorized_callback`) does a plain re-auth redirect instead. `_get_preset_user` is the one path that never got this treatment. Existing test `test_get_preset_user_generic_exception_still_logs_at_error` (using Python's *builtin* `ConnectionError`, not `requests.exceptions.ConnectionError`) explicitly documents this as "unchanged from before" a prior, narrower fix (sc-115333, the 404-specific case) — a gap left by that fix's scope, not a deliberate decision about connectivity errors.
