### Picked: MANAGER-PYTHON-374
**UserNotFoundException: ''** — culprit `UserInternalApiV2.get_workspace_roles_for_user` (well, transaction tag; actual code is `UserInternalApi.get_workspace_roles_for_user` in v1), 50,635 events since 2026-01-13, 0 users impacted. Flagged as a candidate on 07-22 and 07-23 logs but never picked until now.

**Root cause** (`preset/controllers/api/internal/v1/user.py:56-87`, `preset/security/manager.py:1553-1578`):
- `get_workspace_roles_for_user` (called by shell/deployments to check a user's workspace roles) calls `SecurityManager.get_user_roles_for_workspace`, which raises `UserNotFoundException` when `find_user_by_username_or_id` can't resolve the given id (stale/unknown SAML identity, deleted user, eventual-consistency race — legitimate, expected condition).
- The controller already catches this and returns a correct `404`, but logs via `logger.exception(...)` first — ERROR level + full stack trace. Sentry's default `LoggingIntegration` (event_level=ERROR) captures this as an issue regardless of the `handled: yes` tag.
- Confirmed via `grep` that every sibling handler catching this exact exception elsewhere in the codebase (`v2/user.py::delete_user`, `WorkspaceInternalApiV2.get_workspace_user*`, `TeamInternalApi.*`) does `except UserNotFoundException: return self.error_404(...)` with **no logging at all** — this call site was the one outlier.
- Same bug class as MANAGER-PYTHON-2ZF (07-22): an expected/handled condition logged loudly enough for Sentry to capture as noise.

**Fix:** Downgraded `logger.exception` → `logger.warning` (drops the stack trace, keeps the message) in the one `except PresetException` block. Left the broad `except PresetException` catch itself untouched — narrowing it to `UserNotFoundException` specifically would risk turning some other (currently handled-and-404'd) `PresetException` subtype into an unhandled 500, which is out of scope for a log-noise fix and not evidenced by the Sentry issue itself.

**Test:** New `test_get_roles_for_unknown_user_is_not_logged_as_error` in `tests/preset/controllers/api/internal/v1/test_user_api.py` — drives the endpoint with an unresolvable `username_or_id`, asserts the 404 is unchanged, and asserts exactly one WARNING-level record fires (via `assertLogs(level="WARNING")`, following the `assertLogs`/`assertNoLogs` pattern from PR #3872's test). ### Picked: `superset/commands/importers/v1/utils.py:55-62`, function `load_yaml()`
- **Sibling-site drift, same file**: `load_yaml()` (used by `load_metadata()` and `load_configs()` — i.e. every file in an import ZIP: databases, dashboards, charts, datasets, ssh tunnels) only catches `yaml.parser.ParserError`. - **Hierarchy confirmed** (`python3 -c "import yaml; print(yaml.parser.ParserError.__mro__)"`): `ParserError`, `ScannerError`, `ComposerError`, `ReaderError`, `ConstructorError` are all siblings under `yaml.error.YAMLError` — `ParserError` is not a superclass of the others.
- **Repro confirmed empirically**: `yaml.safe_load('key: "unterminated string')` raises `yaml.scanner.ScannerError`, not `ParserError`. Re-ran the exact try/except shape from `load_yaml()` standalone (no Superset import needed — pure stdlib+PyYAML) and confirmed the `ScannerError` leaks past `except yaml.parser.ParserError`, uncaught.
- **Reachability confirmed**: `load_configs()` runs inside `ImportModelsCommand.validate()`, called from `run()` *before* the try/except that wraps `_import()` — so nothing in the command layer catches it. The API layer (`dashboards/api.py` `import_`, and chart/dataset/database equivalents) has no try/except around `command.run()` either; it's wrapped only in FAB's `@safe` decorator, which turns any uncaught exception into a generic opaque 500 ("Fatal error"), discarding the actual reason. Meanwhile the *intended* path (`ParserError` → `ValidationError` → `CommandInvalidError`, `status = 422` in `superset/commands/exceptions.py`) gives a real 422 with the specific "Not a valid YAML file" message. So this is a live raw-500-instead-of-4xx bug, not a defensive/unreachable catch — importing a dashboard/chart/dataset/database ZIP with any malformed (but non-ParserError) YAML file currently 500s.
- **Fix**: widen `except yaml.parser.ParserError` → `except yaml.YAMLError` in `load_yaml()`. No behavior change for the already-working ParserError case; new coverage for Scanner/Composer/Reader/Constructor errors, mirroring `import_tag()`'s existing pattern in the same file.
