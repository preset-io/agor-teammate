### Root cause (verified against `preset-io/superset-shell` master source via `gh api`, not guessed)
Pulled `preset/multi_tenant/workspace_pub_sub.py` (1616 lines) and `preset/tasks.py`. Three sibling Celery-scheduled functions talk to Preset Manager's internal API for a deployment:
1. `push_workspace_status_update()` — **already fixed**, PR #4957 (merged 2026-08-31, SUPERSET-PYTHON-95B): wraps the call in `try/except HTTPError`, swallows 403 with a WARNING + metric, re-raises everything else. This is the style precedent.
2. `poll_workspace_events()` — **partially fixed**: has `try/except HTTPError` but only special-cases `status_code == 404` (swallowed); a 403 falls into `else: raise` — uncaught, matches NME's captured traceback exactly (`tasks.py:325` → `workspace_pub_sub.py:830` → `deployment.py:21 get_workspace_events` → `raise_for_status`).
3. `poll_workspace_updates()` — **no exception handling at all**. Matches 9C8's traceback exactly (`tasks.py:321` → `workspace_pub_sub.py:818` → `deployment.py:16 get_workspace_updates` → `raise_for_status`).

Both poll functions run on a plain Celery beat schedule (no `autoretry_for` — they just fire again next tick), so an unhandled 403 on a single deployment with invalid/revoked credentials (10410) recurs forever — explains the 3-year/2-year chronic volume. `gh search prs "poll_workspace_updates OR poll_workspace_events" --repo preset-io/superset-shell` → 0 results, confirmed nothing in flight.
