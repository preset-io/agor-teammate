### Picked: `SUPERSET-PYTHON-1516` — unhandled `BadRequest` in `get_dataset_id_from_context`

https://preset-inc.sentry.io/issues/7637766668/ — 614 events since firstSeen 2026-07-28, still firing daily, culprit the MCP `get_chart_data` tool.

**Root cause** (verified against source, not guessed): `superset/jinja_context.py::get_dataset_id_from_context()` (backs the `metric()` Jinja macro when no explicit `dataset_id` is passed) read the ambient Flask request via a raw `request.get_json(cache=True) if request.is_json else None`. `request.is_json` only inspects the `Content-Type` header, not whether the body actually parses as JSON. When `metric()` is evaluated while rendering a chart's SQL from the MCP `get_chart_data` tool, the ambient Flask request is the *raw MCP transport request* (`Content-Type: application/json`, but not a chart-data JSON payload) — so `request.get_json()` raised an unhandled Werkzeug `BadRequest` instead of falling through to the function's own `form_data`/`g.form_data` fallbacks. Confirmed via the full Sentry stack trace: `fastmcp` → `mcp_service/auth.py` → `get_chart_data.py` → `get_data_command.py` → ... → `jinja_context.py::process_template` → `metric_macro` → `get_dataset_id_from_context` → `request.get_json` → `on_json_loading_failed` → `BadRequest`.

**Sibling-site-drift, not a novel bug**: this exact bug class was already fixed for the sibling function `get_form_data()` in apache/superset **#42196** (merged 2026-07-28 — the same day this Sentry issue's `firstSeen` starts), which added `superset/views/utils.py::get_request_json_body()` specifically to coerce a non-JSON body to `{}` instead of raising, for this exact MCP-tool-call shape (its own docstring literally describes the `filter_values()` macro version of this same problem). `get_dataset_id_from_context()` had its own separate inline copy of the old unguarded pattern that #42196 never migrated — same bug-class-drift pattern this pipeline has repeatedly found (the `raise_for_access`/`TemplateError` series, the `DetachedInstanceError` series).

**Fix**: two-line change — swap the raw inline `request.get_json()` check for the existing `get_request_json_body()` helper. No new abstraction, reuses the established fix, all downstream fallback logic (`request.form`/`request.args`/`g.form_data`) untouched.

**Test**: `test_metric_macro_no_dataset_id_non_json_body_with_json_content_type` in `tests/unit_tests/jinja_context_test.py`, mirroring #42196's own test shape (`current_app.test_request_context(data="not-json-at-all", content_type="application/json")`). Verified fail-before/pass-after via `git stash` (pre-fix: raw `BadRequest` escapes; post-fix: falls through to the pre-existing `SupersetTemplateException("Please specify the Dataset ID...")`). Full `tests/unit_tests/jinja_context_test.py`: 136/137 passed — the 1 failure (`test_get_time_filter[...trino://mydb...]`) is a pre-existing, unrelated `sqlalchemy.databases` import error in the local trino dialect package, reproduced identically on a clean `master` checkout before restoring the fix (not caused by this diff). `ruff check`/`ruff format --check` clean; `mypy` 1.15.0 (via `uvx`, the default 0.961 in this shared clone chokes on a numpy-stub incompatibility unrelated to this change) clean.

**Tradeoff**: none — this restores the function's own pre-existing "please specify the dataset ID" fallback instead of an unhandled exception; no new failure-mode semantics.
