### Picked: `superset/commands/report/alert.py::AlertCommand._execute_query()` — Jinja render call outside its own try block

**Root cause** (verified empirically, not guessed): `_execute_query()`'s docstring documents `:raises AlertQueryError: SQL query is not valid`, and the method does have a `try: ... except Exception as ex: raise AlertQueryError(...) from ex` wrapping the query-execution flow — but `rendered_sql = sql_template.process_template(self._report_schedule.sql)` was placed as the statement *immediately before* that `try:`, not inside it. Alert SQL (`ReportSchedule.sql`) is a normal user-editable field with documented Jinja templating support. `process_template()` (`superset/jinja_context.py`) converts most template errors to `SupersetSyntaxErrorException`/`SupersetTemplateException`, but has its own bare-`raise` fallback that re-raises a raw `jinja2.exceptions.UndefinedError`/`TemplateError` when its undefined-function-name regex doesn't match (confirmed by reading the function directly — this is the same underlying `process_template()` fallback path that `sqllab/query_render.py` already guards against with a broad `except TemplateError`). Because the call sat outside `_execute_query()`'s try block, ANY of these exceptions — not just the raw-fallback case — would propagate straight past `retry_call(self._execute_query, exception=AlertQueryError, ...)` in `validate()` (which only retries/catches `AlertQueryError` specifically, confirmed by reading `superset/utils/retries.py`), crashing the alert-execution task with a raw exception instead of surfacing the documented, typed error.

**Fix**: 2-line move — `rendered_sql = sql_template.process_template(...)` now the first statement inside the existing `try:` block; `sql_template = jinja_context.get_template_processor(...)` left untouched above it. Additive-only, no behavior change for any alert query that renders successfully today.

**Regression test verified empirically**: wrote `test_execute_query_wraps_template_rendering_error` (mocks `process_template` to raise `jinja2.exceptions.TemplateError`, asserts `_execute_query()` raises `AlertQueryError`). Built a scratch venv (`uv venv` + `uv pip install -e .` — works without mysqlclient since it's an optional `mysql` extra, not a base dependency; had to pin `numpy==1.26.4` over whatever `-e .` resolves by default, or `superset/utils/pandas_postprocessing/utils.py`'s `np.product` reference crashes at import time on newer numpy) and ran the real test suite: confirmed the new test fails on pre-fix code (raises the raw `TemplateError` uncaught, traceback shows it at `alert.py:196` exactly as read) and passes post-fix, alongside all 24 pre-existing tests in the file (25/25 total post-fix).

### Picked: `SUPERSET-PYTHON-B8Y` (73,006 events, `EventTimeoutException`) + `SUPERSET-PYTHON-B8X` (1,306 events, "Timed out waiting for ack for event id"), both at culprit `multi_tenant.send_cloud_event`, 0 users impacted.

**Repo**: `preset-io/superset-shell` (not apache/superset or manager — first time this pipeline has picked a Sentry issue rooted in superset-shell's `preset/` package). Confirmed the exact file/line via `gh search code` against the repo before cloning.

**Root cause (verified via evidence)**:
- `preset/tasks.py`'s `multi_tenant.send_cloud_event` celery task (`autoretry_for=(Exception,)`, `max_retries=13`, exponential backoff to 1h — so up to 14 attempts over ~3h) wraps the broker call in try/except and calls `logger.exception(...)` (ERROR + traceback) on **every** attempt before re-raising for autoretry.
- `preset/app.py::configure_sentry()` wires `LoggingIntegration(level=INFO, event_level=logging.ERROR)` — every one of those ERROR log records becomes a distinct Sentry event. That's the volume driver, not genuine failures.
- Confirmed this manual logging is redundant: `sentry-sdk[celery]==2.33.2` is pinned (`setup.py`), and downloaded+inspected the actual wheel — `CeleryIntegration` is in `_AUTO_ENABLING_INTEGRATIONS` (auto-enables since celery is installed, no override found in `configure_sentry`). Read `sentry_sdk/integrations/celery/__init__.py` from that same wheel: `_capture_exception` explicitly ignores `CELERY_CONTROL_FLOW_EXCEPTIONS` (celery's internal `Retry`, which is what `autoretry_for` raises internally on every in-progress retry attempt) and only captures the exception when celery's retry loop is truly exhausted and re-raises the original exception. So Celery + Sentry's own integration already correctly report only the final genuine failure, automatically — no manual logging needed for that.

### Fix (surgical, one line)
Downgrade `logger.exception("Failed to send cloud event, retrying...")` → `logger.warning(..., exc_info=True)` in `preset/tasks.py`. Traceback still preserved for Datadog debugging; no longer creates a Sentry event per transient auto-retried attempt. `raise` kept unchanged so `autoretry_for` still functions identically. No change to retry count/backoff.
