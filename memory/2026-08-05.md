### Found a real one, but it's outside this pipeline's current repo scope: PLATFORM-BROKER-N

**`IllegalOperationError: Channel closed`** — `preset-inc` project `platform-broker` (Node/TypeScript, `preset-io/platform-broker`, a service never previously touched by this pipeline). First seen 2023-08-10, **51223 occurrences**, still recurring (last seen 2026-08-04T21:41:30Z).

**Root cause** (read the actual repo source, not guessed — cloned `preset-io/platform-broker` to `/tmp/platform-broker-check`):
- `AMQPManager.submitEventToEventStream()` (`src/amqp.ts:208`) calls `this.channel.sendToQueue(...)` **synchronously, with no try/catch**. When the RabbitMQ connection drops, `onConnectionError()` (`src/amqp.ts:319`) kicks off `setupConnection()` to reconnect in the background (retry with backoff, `forever: true`) — but `this.channel` is either `undefined` or stale until that completes.
- The only call site, `MessageRouter.handleEventMessage()` (`src/router.ts:208-223`), calls `this.amqpManager.submitEventToEventStream(msg)` and then **unconditionally** calls `sendAck(..., SUCCESS)` on the next line — it never checks whether the publish actually succeeded.
- If `sendToQueue` throws (channel closed/reconnecting), execution never reaches the `sendAck` call at all. The exception bubbles up to the *outer* handler, `handleWebsocketMessage()` (`src/router.ts:261-271`), whose catch-all does `Sentry.captureException(err)` and **nothing else** — no ack of any kind (neither SUCCESS nor ERROR) is ever sent to the publishing client.
- Net effect: during any RabbitMQ connection blip, in-flight `submitEventToEventStream` calls throw, the event is silently dropped, and the client is left hanging with no ack and no error — a genuine data-loss bug, not "infra noise" (there's no expectation-mismatch here; the code has zero handling for the known-reconnecting-channel case despite already having full reconnect machinery elsewhere in the same file).

**Proposed fix** (designed, not yet implemented): wrap the `submitEventToEventStream` call in `handleEventMessage` in try/catch; on failure, log + increment a new `countPublishMessageFailure()` metric (mirrors the existing `countConsumedMessageFailure()`/`countConsumedMessageSuccess()` pair — `metrics.ts` currently only has a *success* counter for publishes, an existing asymmetry), and send an `EventAckStatus.ERROR` ack back to the client (new `AckErrors.EVENT_PUBLISH_FAILED`) instead of silently dropping — mirrors the existing `EVENT_PUBLISH_NOT_AUTHORIZED` pattern two lines below. This is a genuine failure-mode semantics change (silent-drop → typed error ack) and would need the mandatory Tradeoffs disclosure per SOUL.md.

### Picked: `superset/datasets/api.py::DatasetRestApi.render_dataset_fields()` — narrower-than-needed except clause

**Root cause** (verified empirically, not guessed): `render_dataset_fields()` (used by `GET /api/v1/dataset/<id_or_uuid>?include_rendered_sql=true` to render Jinja macros in a dataset's `sql`/`metrics`/`columns` fields) caught `(TemplateSyntaxError, SupersetSyntaxErrorException)` around each `process_template()` call — narrower than the correct `TemplateError` used at the 6 already-guarded sites above. `jinja2.exceptions.UndefinedError`'s MRO (`UndefinedError -> TemplateRuntimeError -> TemplateError -> Exception`, confirmed via Python MRO check) means it is a `TemplateError` sibling of `TemplateSyntaxError`, not a subclass — so the same `process_template()` bare-raise fallback (attribute/subscript access on an undefined variable, e.g. `{{ foo.bar }}`, doesn't match the function-call regex that would otherwise convert it to `UndefinedTemplateFunctionException`) escaped both this method's catch and the calling view's `except SupersetTemplateException`, surfacing as a raw opaque 500. Confirmed empirically with a standalone jinja2 script (`Environment(undefined=DebugUndefined)`): `{{ foo }}` doesn't raise, `{{ foo.bar }}` raises raw `UndefinedError`, and a simulated `except (TemplateSyntaxError, ...)` block does not catch it.

**Fix**: widened to `(TemplateError, SupersetSyntaxErrorException)`, matching the established pattern exactly. Additive-only — `SupersetSyntaxErrorException`/`SupersetTemplateException` aren't `jinja2.TemplateError` subclasses, so no currently-working path changes behavior.
