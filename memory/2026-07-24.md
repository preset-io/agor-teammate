### Picked: SUPERSET-PYTHON-YDB
`DatabaseError: ... Cannot parse '' as CloudRegion` — BigQuery REST API 400 rejection, ~90k occurrences / 24 users, firing since 2025-12-11, `apache/superset`.

**Root cause**: `DatetimeFormatDetector.detect_column_format()` (`superset/datasets/datetime_format_detector.py`) opportunistically samples a temporal column to precompute its datetime format on dataset save. It already wraps its entire body in `except Exception: logger.exception(...); return None` — fully handled, zero user-facing impact either way. The Sentry-captured error is a customer's misconfigured/unreachable BigQuery connection rejecting the sampling query (traced the exception chain down to a genuine 400 from BigQuery's `jobs.query` REST endpoint, not a Superset-side bug — confirmed by reading the actual `db_engine_specs/bigquery.py` and `sqlalchemy-bigquery`'s `parse_url.py`/dialect code). Because the whole method shared one broad except, this expected/environmental, already-handled failure got logged at ERROR with a full traceback on every occurrence, and Sentry's logging integration captured it as an issue every time.

**Fix**: narrowed scope — wrap only `database.get_df()` in its own try/except, log at WARNING (matching the level already used by sibling "No data returned"/"Could not detect format" cases a few lines below) instead of ERROR+exception. Outer `except Exception` untouched, so genuine internal bugs (SQL building, quoting, `detect_datetime_format` itself) still log at ERROR and stay visible. No functional/return-value change.

### Environment notes / learnings for next run
- **Sentry MCP access is session-specific, not durable.** This interactive session had `mcp__sentry__*` tools available directly (unlike the 07-23 scheduled run, which had none). Still unresolved whether the daily 8am schedule (`019f8be3`) has this fixed — if tomorrow's scheduled run blocks again, this needs to go to Elizabeth as an infra fix, not another "blocked" log entry.
- **Fresh Agor clone-mode branches need `sg agor_wt_<branch-shortid>` for ALL writes**, not just a one-time gotcha: this includes the Edit/Write tool's own file writes (which run in-process and can't pick up a group added mid-session — every actual file mutation had to go through a `sg agor_wt_... -c 'python3 <script>'` wrapper instead of the Edit tool directly), `git add`/`commit`/`push`, and `ruff` (which needs to create a `.ruff_cache/` in the worktree). Confirmed `sg <group> -c '...' < /dev/null` is the reliable invocation (redirect stdin from /dev/null to avoid an interactive password prompt even though the group has no actual password — that prompt only appears because the *current shell process* predates the group being added to `/etc/group`, not because of a real auth requirement).
- **Do not write ad hoc scratch scripts to `/tmp` directly** — `/tmp` is shared across many concurrent agent sessions/worktrees on this box (dozens of `/tmp/pr*`, `/tmp/superset-*` dirs from other sessions), and a `cat > /tmp/foo.py` can silently fail with `Permission denied` if a same-named file already exists owned by another session, causing a *stale, unrelated* script to execute instead with a confusing traceback. Use `~/tmp_scratch/` (own home dir) for scratch scripts instead.
- **Borrowing a sibling worktree's venv for tests**: had to find one with `sqlglot>=30.12.0` (current `apache/superset` master pin) — many stale venvs floating around pin `sqlglot==28.10.0`/`30.8.0` and fail with a `TypeError: Cannot create a consistent method resolution order (MRO)` on `superset.sql.dialects.dremio` import. `/tmp/soraya-fix-venv` had a matching pin and worked; run with `PYTHONPATH=<worktree-path>:$PYTHONPATH <venv>/bin/python -m pytest ...` from within the worktree so `import superset` resolves to the fix branch, not wherever the venv's editable install originally pointed.
