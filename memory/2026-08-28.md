Per `skills/superset-error-cleanup.md`. Pre-flight: read memory 08-14 through 08-27 for the standing backlog/skip-list. `gh pr list --repo apache/superset --author eschutho --state open --search "in:title exception OR error"` — same ~25 known open PRs, no overlap.

### Picking

Dispatched an Explore agent for a fresh sibling-site-drift sweep. It returned 3 candidates (`commands/report/base.py` unguarded `json.loads` on `dashboard.position_json`, `commands/database/update.py` unguarded `json.loads` on `encrypted_extra`, and a `croniter` narrow-except in `commands/report/base.py`) — verified all three myself and **rejected all three as unreachable**:
- `croniter`: `reports/schemas.py::validate_crontab` already runs `croniter.is_valid()` at the marshmallow schema layer before the command layer ever sees the value — a malformed cron 400s before `commands/report/base.py::validate_report_frequency` is reached.
- `commands/database/update.py` `encrypted_extra` json.loads: the value is schema-validated JSON (`masked_encrypted_extra_validator`) before it reaches `db_engine_specs/base.py::unmask_encrypted_extra`, which itself already catches `(TypeError, JSONDecodeError)` and falls back to returning the (already-valid) input unchanged — no path left for `update.py:135`'s `json.loads` to see malformed JSON.
- `commands/report/base.py` `position_json`: written via `dashboards/schemas.py`'s `position_json` field with `validate=validate_json` at every write path I could find (direct API, YAML import via `json.dumps`) — no confirmed way to get an actually-malformed string into the DB. Weaker "defensive catch for something that can't happen" per the skill's explicit guardrail; declined to force it.

Went back to first principles on the skill's own listed grep (`check_query_access|check_chart_access|check_access`) plus a broader look at `raise_for_access`-adjacent SQL-parsing call sites, and found a genuinely new one: **`superset/sql/parse.py::SQLStatement.parse_predicate`** (~line 1534-1542) calls `sqlglot.parse_one(predicate, dialect=self._dialect)` completely unguarded. **Sibling in the same file**: `SQLStatement._parse()` classmethod (~line 846-893) already catches `sqlglot.errors.ParseError`/`SqlglotError` and converts to the existing `SupersetParseError` — `parse_predicate` never got the same treatment.

**Reachability, verified layer by layer, not assumed**:
- `parse_predicate` is called from `superset/utils/rls.py::apply_rls()` for every RLS predicate on a table referenced by a query.
- Traced every `apply_rls` caller: `sql_lab.py:469` and `sql/execution/executor.py`'s synchronous `execute()` already sit behind broad `except Exception` safety nets a few frames up (`get_sql_results`, `SQLExecutor.execute`) — already degrade gracefully today, not today's target. `models/helpers.py:3541` (virtual dataset RLS) already has its own `except Exception` fail-closed handler. `executor.py`'s `execute_async()` calls `_prepare_sql`→`_apply_rls_to_script` fully unguarded, but has **zero production callers** in the OSS tree today (only unit tests) — not a currently-reachable path, declined as the fix target despite the asymmetry with sibling `execute()`.
- The genuinely reachable, currently-unguarded, end-to-end path: `POST /api/v1/sqllab/estimate/` (`RLS_IN_SQLLAB` flag) → `SqlLabRestApi.estimate_query_cost()` → `QueryEstimationCommand.run()` → `_apply_sql_security()` → `apply_rls()` → `parse_predicate()`, all unguarded. Confirmed `estimate_query_cost` has **no** flask-appbuilder `@safe` decorator (checked its full decorator stack against sibling `get()` in the same class, which does have `@safe`) — so an uncaught `SupersetErrorException` subclass actually reaches Superset's own registered `@app.errorhandler(SupersetErrorException)` (`views/error_handling.py`) for a proper typed response, meaning the root-level fix alone (no API-layer catch needed) is sufficient here, unlike the `explore/permalink`/`form_data` fixes which needed a second file.
- Verified the raw leak empirically pre-fix (own repro, not just reasoning): `SQLStatement("SELECT 1", "postgresql").parse_predicate("a >")` raised `sqlglot.errors.ParseError` uncaught. Needed a proper env for this — fresh `uv venv` + `-e ./superset-core -e .` + pinned `flask-caching==2.4.1` (the `-e .` pyproject resolution alone picks an incompatible flask-caching); documented the recipe in the implementation-session prompt for reuse.
