### Picked: `SUPERSET-PYTHON-X5R` (4844 events all-time, 29 users) + `SUPERSET-PYTHON-X5Q`/`X5P`/`X5N` (same root cause, fingerprint-split siblings)
Found via the user-count sort (all 4 had low 14d event counts but meaningful all-time volume and real user impact — would have been missed by frequency-sort alone).

**Repo**: `preset-io/superset-shell`, `preset/security/manager.py`.

**Root cause** (verified via evidence, not guessed): `_get_preset_user()` calls `self._manager_client.workspaces.get_workspace_user(...)`, which (confirmed by downloading and reading the actual pinned `api-clients` private package source, `clients/base.py::request()`) calls `response.raise_for_status()` with no exception translation — a 404 (user genuinely removed from / not yet provisioned in the workspace, a routine/expected condition already handled correctly downstream via `UserLookupError("No access")`) propagates as a plain `requests.exceptions.HTTPError`. The method's bare `except Exception: logger.exception(...)` logs this — and every other failure — at ERROR with a full traceback. Confirmed via `git log -p` on the exact lines that this is the *same noise class* as sc-115333/PR #4653 (`fix(security): distinct logging for unknown Manager roles...`), which fixed a sibling noise source 140 lines below in `upsert_role()` but never touched this earlier call site where the HTTPError actually originates.

**Fix**: catch `HTTPError` explicitly; if `.response.status_code == 404`, log at WARNING (no traceback); every other failure (non-404 HTTPError, generic exceptions) keeps the original `logger.exception` ERROR path unchanged. Additive-only — `_get_preset_user` still returns `None` on any failure, so access-control behavior is identical; only log severity/verbosity changes for the specific 404 case.
