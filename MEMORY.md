## Lessons Learned

- **A dotted-attribute grep doesn't rule out a field being read.** When checking whether a frontend `buildQuery.ts` reads a form-data field before renaming/removing it, `grep "formData.groupby"` or `grep "\.groupby\b"` misses object-destructuring (`const { groupby } = formData`), which is a completely different literal pattern. Grep for the bare field name too, or better, read the function. Cost real risk on 2026-08-31: a first-pass fix would have silently dropped the grouping dimension from 10 production example charts (Timeseries/Treemap plugins) had self-review not caught the destructuring pattern.
- **`gh pr view --json state` before trusting a memory log's "merged precedent" label.** An earlier day's log called PR #43468 a "merged precedent" when it was actually still open (`DIRTY`/`CONFLICTING`, never merged) — that PR itself contains a live bug (renamed `groupby`→`columns` in a `box_plot` chart YAML, which the box_plot buildQuery treats as a separate, still-active field). Don't inherit a prior day's characterization of a PR's status without re-verifying it live.
- **`groupby`-deprecation noise in apache/superset now has three separate open PRs chasing it (#43468 08-24, #43520 08-25, #43723 08-31), all opened *after* the actual root-cause fix (#41204, merged 2026-06-18) should have already stopped new occurrences at the source.** Before picking a Datadog-driven "deprecation warning" or "groupby" fix in this repo again: (1) `gh pr list --search "query_object OR groupby deprecated"` first — this exact symptom has been re-discovered independently multiple times because the standard `gh pr list --author @me` pre-flight only catches same-author collisions, not same-symptom ones; (2) treat the underlying Datadog volume as possibly stale — it may reflect a `superset-private` build that hasn't merged #41204 yet, not a live apache/superset gap, and that's unverifiable from this checkout alone (superset-private isn't a registered/accessible repo here). 2026-09-02's self-review caught this before a 4th duplicate PR was opened. **Update 2026-09-03:** #43520 is itself the right generic fix for the *whole* `DEPRECATED_FIELDS` family in `query_object.py` (log-level downgrade, not per-field fixture renaming) — it covers `timeseries_limit`/`granularity_sqla` too, not just `groupby`. - **`agor_sessions_spawn` from the private-sre branch fails with "Cannot resolve session-sharing authority for this branch" for any subsession that needs to work in a different repo (e.g. apache/superset).** Workaround (2026-09-04, md5-deprecation-warning fix): create a dedicated `storage_mode: clone` branch on the target repo via `agor_branches_create` (boardId = SRE board), then use `agor_sessions_create` with that branch's `branchId` (not `agor_sessions_spawn`, which always inherits the *calling* session's branch) plus `callbackSessionId` set to the current session for the completion notification. - **Pushing a branch built on current `origin/master` to the `eschutho` fork can fail with a GitHub "refusing to allow a Personal Access Token to create or update workflow ... without `workflow` scope" error**, because the `eschutho` fork's own `master` is far behind upstream (~2636 commits as of 2026-09-04) and the push would introduce every intervening commit including old `.github/workflows/*` changes — `gh repo sync` hits the identical wall. Fix used successfully: rebase the fix commit(s) onto an already-fork-synced ancestor commit whose copies of the changed files are byte-identical to current master (`git rebase --onto <fork-synced-ancestor-sha> <old-base> <branch>`), so the pushed history contains only the real commit and no workflow-file diffs. Worth flagging to Elizabeth as a recurring friction point if it keeps recurring — the underlying fix would be getting `workflow` scope added to the `eschutho` PAT, or periodically syncing the fork through a path that carries that scope.
- **Not every apache/superset PR needs the eschutho-fork push workaround — check `gh api repos/apache/superset/pulls/<N> --jq '.head.repo.full_name'` before assuming the PAT workflow-scope wall applies.** Some PRs (e.g. #43934, 2026-09-08) have their head branch living directly on `apache/superset` itself (pushed there originally, not via a fork), in which case `git push origin <branch>` works immediately with no PAT scope issue at all — the wall only bites when the head repo is `eschutho/superset`. Confirmed the wall still holds in the fork case the same day (PR #43723: merging current `origin/master` into its branch touches 58 `.github/workflows/*` files, same shape as the documented friction) — so this isn't "the wall is fixed," just "check which case you're in before you assume it applies."
- **Update 2026-09-09: the fork-push wall isn't only about merging old history in — a *fresh* branch cut straight from current `origin/master`, touching only 2 non-workflow files, still hit it** (`fix-database-extra-validator-non-dict` → PR #44092, blocked on `asf-allowlist-check.yml`). The eschutho fork's own default branch is ~2600+ commits behind, so pushing a new branch built on current master introduces *every* `.github/workflows/*` file as "new" content from the fork's perspective (not a diff against fork history) — the PAT's missing `workflow` scope blocks that regardless of how minimal the actual code diff is. - **Datadog Sensitive Data Scanner sampling defaults to 100%, and a live `rate = 100` is indistinguishable from "unset" — so a plan showing `- samplings { rate = 100 }` on a `datadog_sensitive_data_scanner_group` is almost always cosmetic false drift, not a real scan-coverage drop.** Derived 2026-09-11 from the DataDog/terraform-provider-datadog source while assessing terraform-live-envs PR #2363 (garciajrx flagged the Komgo PII scanner's `- samplings { rate = 100 }` as a Komgo-contract risk). Facts: (1) the provider hardcodes `const defaultSensitiveDataScannerSamplingRate = 100.0`; sampling is an **opt-in reduction** (valid UI range 10–99%) — no `samplings` entry for a product = that product scanned at 100%. (2) Datadog's API **omits** 100% samplings from responses because 100% == the implicit default. (3) So omitting/removing a `rate = 100` block reverts to the 100% default → **zero behavior change**; you can't drop *below* 100% by omission (100% is the floor). (4) The drift only *appears* because terraform-live-envs pins datadog provider **3.72.0**, which does a naive diff; a newer provider added `reconcileTerraformSamplings` logic that explicitly *"ignore[s] implicit default (100%) samplings"* so this false drift stops showing (verified: v3.72.0 lacks that function, master has it). **Takeaway for SDS drift:** don't treat a `-samplings{rate=100}` line as a coverage regression. Options: (a) let the apply drop the redundant live entry — a true no-op that *self-heals* the false drift (API then returns nothing → clean future plans, no config churn); (b) codify `samplings { product = "logs" rate = 100 }` to silence the line without applying; or (c) bump the datadog provider past the reconcile-logic version (bigger blast radius). **On #2363 we chose (a)** — leave TF as-is, let it clear on apply.
